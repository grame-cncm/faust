# Faust benchmark framework

## Overview

This directory contains a small benchmark and inspection framework for Faust-generated DSP code.

The framework has two main execution modes:

- `bench`: generate runnable benchmark programs, execute them, and collect reports.
- `inspect`: generate low-level artifacts, i.e. LLVM IR and ASM, around the generated `compute` code.

The two modes intentionally use different Faust architecture files. Benchmark architectures measure runtime
behavior. Inspect architectures keep the generated program minimal so the produced low-level code is easier
to read and compare.

The framework is backend-oriented: each supported language has a clear place for its architecture files,
OUT generation, binary build, benchmark execution, and optional inspection logic.

## Directory layout

Current intended layout:

```
faust/architecture/_bench/
  arch/
    cpp/
      bench.cpp
      bench.h
      common.h
      inspect.cpp
    mojo/ -> ../../mojo
      bench.mojo
      inspect.mojo
  script/
    source.sh
    bench.sh
    csvmanip.py
    plot.py
  src/
    *.dsp
  report/
    report.csv
    bin/
      *_bin_cpp
    tab/
      cpp/
      mojo/
    tmp/
      *.csv
      *.build.log
    plot/
      *.svg
    snap/
      <timestamp>_<snapshot_name>/
    llvm/
      cpp/
      mojo/
    asm/
      cpp/
      mojo/
```

The `arch/<lang>/` directories contain the Faust architecture files used by the framework. The exact
internal organization of each backend is language-specific: a backend may use headers, helper files,
symlinks, packages, or modules.

The Mojo backend is reached through the `arch/mojo` symlink. This is part of the framework contract and
must not be replaced by a copied directory or bypassed with unrelated paths.

## Naming model

The framework uses a few internal names with precise meanings.

`SRC` means the original Faust DSP input:

```
src/<name>.dsp
```

`arch` means the Faust architecture wrapper:

```
arch/<lang>/bench.*
arch/<lang>/inspect.*
```

`OUT` means the target-language file generated by Faust from a SRC file and an architecture:

```
arch/cpp/<name>_<mode>_out.cpp
arch/mojo/<name>_<mode>_out.mojo
arch/cpp/<name>_<mode>_insp.cpp
arch/mojo/<name>_<mode>_insp.mojo
```

`bin` means the executable produced from a benchmark OUT file:

```
report/bin/*_bin_cpp
arch/mojo/*_bin_mojo
```

Mojo binaries stay under `arch/mojo` because the generated Mojo program depends on the symlinked
architecture/package layout. C++ binaries are stored in `report/bin`.

## Setup

Enter the benchmark workspace and activate the environment:

```
pixi shell
source script/source.sh
```

The environment should provide Faust, Mojo, Python, pandas, matplotlib, and a C++ compiler.

`source.sh` initializes paths, creates report directories, checks the Mojo architecture link, and loads the
benchmark API from `script/bench.sh`.

## Public API

The framework exposes the following public commands:

```
bench_run <modes> <langs> <sample_rates_khz> <buffer_sizes> <sources...>
bench_clean
bench_plot <plot_name>
bench_snapshot <snapshot_name>
inspect_llvm_gen <modes> <langs> <sources...>
inspect_asm_gen <modes> <langs> <sources...>
```

All other shell functions are internal helpers.

### `bench_run`

Run benchmarks and generate reports.

```
bench_run all all all all all
bench_run scalar all 48 64 all
bench_run vec mojo 48 64 bells
bench_run scalar,vec cpp,mojo 48,192 64,512 carre_volterra
```

Arguments:

- `modes`: `all`, `scalar`, `vec`, or comma-separated entries from `BENCH_MODES`.
- `langs`: `all` or comma-separated entries from `BENCH_LANGS`.
- `sample_rates_khz`: `all`, `48`, `192`, or comma-separated values.
- `buffer_sizes`: `all`, a single integer, or comma-separated integers.
- `sources`: `all`, DSP names, DSP paths, or shell-expanded globs.

Precision is not passed as an argument. Each benchmark run executes all configured precisions, currently
`f32` and `f64`.

The benchmark run prints an immediate startup message, then executes the full workflow. OUT generation and
binary builds are parallelized. Benchmark execution is kept serial to preserve timing quality.

### `bench_clean`

Clean the current benchmark report state and generated temporary artifacts.

It removes:

```
report/report.csv
report/tmp/*
report/tab/*
report/bin/*
report/plot/*
report/snap/*
report/llvm/*
report/asm/*
arch/cpp/*_out.cpp
arch/cpp/*_insp.cpp
arch/mojo/*_out.mojo
arch/mojo/*_insp.mojo
arch/mojo/*_bin_mojo
```

### `bench_plot`

Generate an SVG plot from the current global CSV.

```
bench_plot tput_48k_64
```

The output is written to:

```
report/plot/<plot_name>.svg
```

### `bench_snapshot`

Save the current report state.

```
bench_snapshot after_changes
```

Snapshots are written to:

```
report/snap/<timestamp>_<snapshot_name>/
```

A snapshot copies the current CSV, tab reports, plots, and a metadata file describing the run context.

### `inspect_llvm_gen`

Generate LLVM IR using the inspect architecture.

```
inspect_llvm_gen all all carre_volterra
inspect_llvm_gen scalar mojo all
```

Outputs are written to:

```
report/llvm/<lang>/<dsp>_<mode>_<precision>.ll
```

### `inspect_asm_gen`

Generate target assembly using the inspect architecture.

```
inspect_asm_gen all all carre_volterra
inspect_asm_gen vec cpp,mojo bells
```

Outputs are written to:

```
report/asm/<lang>/<dsp>_<mode>_<precision>.s
```

## Benchmark workflow

The benchmark workflow is:

```
.dsp SRC
  -> Faust + bench architecture
  -> generated backend OUT
  -> compiler
  -> executable
  -> human-readable .tab report
  -> temporary CSV fragment
  -> merged report/report.csv
  -> optional plot or snapshot
```

For each selected DSP SRC, language, and mode, the framework first generates backend OUT files using the
language's `bench` architecture. OUT generation is scheduled in parallel across the selected matrix.

It then builds benchmark binaries for each sample-rate, buffer-size, and precision case. Builds are also
scheduled through a global parallel queue. The number of build jobs is controlled internally by
`BENCH_JOBS`, defaulting to `10`.

Benchmark binaries are executed serially. This avoids timing contamination from CPU contention, scheduler
noise, shared cache pressure, and thermal/frequency effects.

The executable prints a human-readable report. The shell script redirects that output into a `.tab` file.
If CSV writing is enabled, the executable also appends a headerless CSV row to a temporary fragment. The
Python CSV helper then merges each fragment into the global report CSV.

Unless `BENCH_KEEP_TMP=1` is set, generated OUT files and benchmark binaries are automatically deleted
after successful runs.

## Inspection workflow

The inspection workflow is:

```
.dsp SRC
  -> Faust + inspect architecture
  -> generated inspect OUT
  -> compiler --emit llvm / --emit asm
  -> report/llvm/<lang>/ or report/asm/<lang>/
```

Inspection is not benchmarking. Its purpose is to expose the low-level shape of the generated `compute`
code with as little benchmark/report/runtime noise as possible.

`inspect_llvm_gen` and `inspect_asm_gen` use the language's `inspect` architecture, not its `bench`
architecture. Inspect OUT files are temporary and are deleted after emission unless `BENCH_KEEP_TMP=1` is
set.

## Architecture contract

### Architecture lookup

For each supported language, the framework expects two architecture entry points:

```
arch/<lang>/bench.*
arch/<lang>/inspect.*
```

Examples:

```
arch/cpp/bench.cpp
arch/cpp/inspect.cpp
arch/mojo/bench.mojo
arch/mojo/inspect.mojo
```

The exact set of auxiliary files is not prescribed by the framework. For example, the C++ backend may
split behavior across headers, while Mojo may use modules imported through the symlinked architecture tree.

### Bench architecture

A bench architecture must generate a runnable program that:

- instantiates the Faust-generated DSP;
- initializes it with the configured sample rate;
- allocates input and output buffers;
- optionally fills input buffers;
- runs warmup iterations;
- measures repeated calls to `compute`;
- computes an output checksum;
- prints a human-readable report;
- optionally writes one headerless CSV row for each run case.

The language implementation should provide behavior equivalent to:

```
fill_inputs
warmup
measure
checksum_outputs
print_report
write_csv
```

The names can differ by language if needed, but the behavior and report model must stay aligned.

A bench architecture is allowed to contain benchmark-specific machinery: timing loops, adaptive batching,
report printing, CSV writing, checksums, and compiler optimization barriers.

### Inspect architecture

An inspect architecture must generate a minimal runnable program that:

- instantiates the Faust-generated DSP;
- initializes the DSP and buffers;
- calls the generated `compute` path through a clearly identifiable entry point;
- avoids benchmark reporting, CSV writing, plotting, and adaptive timing logic;
- keeps enough optimizer barriers to prevent the compute path from being removed;
- makes LLVM IR or assembly output easy to inspect.

The core behavior is:

```
inspect_compute
```

This entry point should be easy to find in generated low-level output. It should isolate the generated DSP
compute path as much as reasonably possible.

## Reports and outputs

Main output paths:

```
report/tab/<lang>/*.tab
report/report.csv
report/tmp/*.csv
report/plot/*.svg
report/snap/<timestamp>_<name>/
report/llvm/<lang>/*.ll
report/asm/<lang>/*.s
```

Meaning:

- `.tab` files contain the human-readable output of each benchmark executable.
- `report/report.csv` is the global structured benchmark report.
- `report/tmp/*.csv` files are temporary headerless CSV fragments.
- `report/plot/*.svg` contains plots generated from the global CSV.
- `report/snap/` stores copies of the current report state.
- `report/llvm/` and `report/asm/` contain inspection artifacts.

## CSV model

Each backend writes headerless temporary CSV rows. The script layer owns the final CSV header and merge
policy.

The global CSV stores:

- identity fields: language, DSP, case, mode, precision, optimization;
- configuration fields: sample rate, buffer size, input/output count;
- timing fields: elapsed time, nanoseconds per compute, frame, and output sample;
- spread fields: fast, slow, absolute spread, percent spread;
- throughput fields: frames per second and output samples per second;
- validation field: checksum.

All languages must write rows in the same column order.

Temporary CSV fragments are merged into `report/report.csv` by replacing rows with the same benchmark
identity. This makes repeated runs deterministic and avoids appending stale duplicate rows.

## Plot model

Plots are generated from `report/report.csv`.

The default plot uses output-sample throughput:

```
out_samp_per_s
```

Values are normalized per DSP/configuration group so different languages, modes, and precisions can be
compared visually. Fast and slow throughput values are drawn as whiskers when available.

## Adding a new backend

To add a new language backend:

1. Add the language name to `BENCH_LANGS`.
2. Add a bench architecture under `arch/<lang>/bench.*`.
3. Add an inspect architecture under `arch/<lang>/inspect.*`.
4. Implement OUT generation for the bench architecture.
5. Implement OUT generation for the inspect architecture.
6. Implement benchmark build and execution logic.
7. Implement LLVM and assembly generation if the backend supports them.
8. Ensure the backend writes the same CSV schema as the other languages.

The split is fixed:

```
bench_run
  uses the bench architecture

inspect_llvm_gen
inspect_asm_gen
  use the inspect architecture
```

## Useful overrides

Common overrides:

```
BENCH_KEEP_TMP=1
BENCH_JOBS=10
BENCH_SAMPLE_RATES=(48000 192000)
BENCH_BUFFER_SIZES=(64 512)
BENCH_WARMUP_ITERS=50
BENCH_COMPUTE_ITERS=1000000
BENCH_MAX_BATCH_SIZE=10000
BENCH_INSPECT_COMPUTE_ITERS=1
```

Compiler options are configured through:

```
BENCH_CPP_OPT
BENCH_MOJO_OPT
```

## Notes

The benchmark and inspect architectures intentionally serve different purposes.

The benchmark architecture should produce trustworthy measurements and structured reports. The inspect
architecture should expose the generated low-level code with minimal noise.

Do not use inspect output as a performance measurement. Use it to understand code generation, compiler
behavior, and optimization differences between backends.
