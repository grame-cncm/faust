# Faust to Mojo architectures

This directory contains the architectures and support components used by the FAUST Mojo backend to turn
transpiled DSP code into an executable program.

A FAUST backend is composed of two main parts:

- the **generator**, which translates the FAUST intermediate representation into the target language;
- the **architecture system**, which provides the environment required to use the generated DSP.

In the case of the Mojo backend, the generator mainly produces the `struct mydsp`, containing the state,
initialization operations, metadata, user interface description, and the `compute` kernel.

The architectures in this directory instead provide the components external to the DSP: audio drivers,
user interfaces, buffer management, support functions, and application entry points.

This keeps the processing code independent from the context in which it is executed. The same DSP can
therefore be embedded in different architectures without modifying the code produced by the generator.

## FAUST architectures

A FAUST architecture is a file written in the target language (in this case Mojo) and used as a template
during compilation. The file contains the code required to use the DSP and two points where the compiler
inserts the generated code:

```
    <<includeIntrinsic>>
    <<includeclass>>
```

In the Mojo case, only `<<includeclass>>` is actually replaced. The injected code is the output of

```
    MojoCodeContainer.produceClass()
```

however, `<<includeIntrinsic>>` is also used in the files for the compiler to work correctly.

A normal Mojo architecture therefore has the following form:

```
    code provided by the architecture
    |
    |--> imports, types, and support components
    |
    code generated by FAUST
    <<includeIntrinsic>>
    <<includeclass>>
    |
    |--> the tags are replaced with the struct
    |
    code provided by the architecture
    |
    |--> main, driver, allocation, and execution control
    |
    EOF
```

The files `portaudio.mojo`, `portaudio-terminal.mojo`, `bench.mojo`, `inspect.mojo`, and `impulse.mojo`
all follow this scheme. What changes is the code surrounding `mydsp` and, consequently, the purpose of the
resulting program.

This separation is particularly important in the FAUST model: the generator does not need to know the
audio driver, the user interface system, or the benchmark framework being used. It only produces a DSP
conforming to the contract expected by the architectures.

In this context, the support code contained in the subdirectories of `architecture/mojo` is also considered
architecture code. These modules provide the internal implementation of the architecture components and are
used by the templates located directly in `architecture/mojo`.

The templates are passed to the FAUST compiler through the `-a` option to build the complete Mojo program
around the generated DSP.

## DSP interface

The common contract between the generated DSP and the architectures is represented by the `FaustDsp` trait,
declared in `dsp/dsp.mojo`.

The trait describes the operations that a generated DSP class must provide. These include:

- accessors for sample rate, number of inputs, and number of outputs;
- instance initialization and reset operations;
- metadata and JSON description generation;
- user interface construction;
- the `compute` method, which performs DSP computation on a block of samples.

The main computation interface is conceptually:

```
    dsp.compute(count, inputs, outputs)
```

where `count` indicates the number of frames to process and `inputs` and `outputs` respectively represent
the input and output streams.

The relationship between generator and architectures can be summarized as follows:

```
    FAUST program
    |
    FAUST compiler
    |
    +------------------+
    |                  |
    Mojo generator     |
    |            architecture file
    struct mydsp       |
    |                  |
    +--------+---------+
    |
    complete Mojo file
    |
    Mojo compiler
    |
    application
```

The architectures therefore do not depend on the internal implementation of a particular DSP, but only on
the common interface exposed by the generated class.

## Organization into Mojo modules and packages

Mojo distinguishes between **modules** and **packages**. A `.mojo` file can be used as a module, while a
directory is recognized as a package when it contains an `__init__.mojo` file.

This directory uses that organization to separate the different responsibilities of the architecture.

```
    architecture/mojo/
    ├── audio/
    │   ├── __init__.mojo
    │   └── portaudio/
    ├── conf/
    │   ├── __init__.mojo
    │   └── prelude.mojo
    ├── dsp/
    │   ├── __init__.mojo
    │   └── dsp.mojo
    ├── gui/
    │   ├── __init__.mojo
    │   ├── gui.mojo
    │   ├── terminal.mojo
    │   └── control.mojo
    ├── help/
    ├── mem/
    ├── meta/
    ├── bench/
    ├── test/
    ├── portaudio.mojo
    ├── portaudio-terminal.mojo
    ├── bench.mojo
    ├── inspect.mojo
    └── impulse.mojo
```

The `__init__.mojo` files expose the public interface of the corresponding package, generally by re-exporting
definitions from the internal modules. This allows top-level architectures to use compact imports:

```
    from conf import *
    from dsp import *
    from gui import *
    from meta import *
```

### Location of transpiled files

The architectures import local packages such as `conf`, `dsp`, `gui`, `meta`, `mem`, and `audio`. To make
these packages available to the Mojo compiler, `architecture/mojo` must be included in the search path
through the `-I` option.

For example, after expanding `portaudio.mojo`, the transpiled file contains:

```
    from conf import *
    from dsp import *
    from gui import *
    from meta import *
    from audio.portaudio import *
```

The transpiled file can be generated in any directory, provided that the path containing the architecture
packages is supplied during compilation:

```
    mojo build -I architecture/mojo path/to/generated_dsp.mojo -o generated_dsp
```

## Pixi environment

The directory is also a standalone Pixi workspace. The `pixi.toml` file defines the environment in which
the Mojo architectures are compiled and executed.

The manifest uses the channels:

```
    channels = [
        "https://conda.modular.com/max-nightly",
        "conda-forge"
    ]
```

and installs nightly versions of `modular` and `mojo`. The workspace is configured for `osx-arm64`.

The environment can be installed and activated from the directory with:

```
    pixi install
    pixi shell
```

A command can also be executed directly in the environment through `pixi run` (`pixi run mojo build ..`).

The `pixi.lock` file stores the concrete dependency resolution and allows the same environment to be
reconstructed from the manifest.

## Common components

The subdirectories implement reusable components shared by the different top-level architectures.

### Configuration

The `conf` package contains common definitions required by both the generated code and the architectures.

The `conf/prelude.mojo` module centralizes in particular:

- aliases for the arithmetic types used by the backend;
- `DType` types and constants;
- aliases for SIMD types;
- pointer types and their origins;
- audio stream representations;
- constants related to alignment and memory;
- the definition of the external `DFAUST` precision.

The architecture precision is configured at compile time through the option:

```
    -D DFAUST=DType.float32
```

The type is then retrieved in the code through `get_defined_dtype`:

```
    comptime dfaust = get_defined_dtype["DFAUST", DType.float32]()
```

and used to define `FaustFloat`:

```
    comptime FaustFloat = Scalar[dfaust]  # SIMD[dfaust, 1]
```

`FaustFloat` therefore represents the numerical type used by the architecture and takes the precision
specified through `DFAUST`; if the option is not provided, `f32` is used.

### DSP

The `dsp` package defines the `FaustDsp` trait, which represents the contract between the code produced by
the generator and the rest of the architecture.

The architectures can therefore be written generically with respect to the concrete DSP type. The audio
driver, for example, only requires a type conforming to `FaustDsp` and can invoke its accessors and
`compute` method without knowing the fields or operations generated for a particular FAUST program.

### Audio

The `audio` package contains the abstraction of the audio driver.

The `audio/audio.mojo` module defines the `FaustAudio` trait, composed of the operations:

```
    init
    start
    stop
```

A concrete audio driver implements this contract and receives a DSP conforming to `FaustDsp`.

The `PortAudio` implementation is located in the `audio/portaudio` package, further divided into:

- `ffi.mojo`, which exposes the definitions required to interact with the PortAudio C API;
- `portaudio.mojo`, which implements the `PortAudio` driver and FAUST-specific helpers.

The driver initializes `PortAudio`, selects the input and output devices, builds the stream parameters, and
registers a callback associated with the DSP instance.

When a new audio block arrives, the callback converts the buffers received from PortAudio into the
representation expected by the backend and calls:

```
    dsp[].compute(S32(count), inputs, outputs)
```

The audio thread therefore becomes responsible for the real-time invocation of the generated kernel.

### GUI

The `gui` package defines the user interface abstraction through the `FaustGui` trait.

The trait reproduces the operations used by the FAUST UI system to describe widget hierarchies, active
controls, bargraphs, and metadata. Most operations have an empty implementation, so a concrete GUI can
implement only the functionality it requires.

The `build_user_interface` method generated inside `mydsp` receives an implementation of `FaustGui` and
registers the DSP parameters with it. The zones associated with the controls directly reference fields of
the DSP structure, allowing an interface to modify the parameters used by `compute`.

No significant development time was invested in building a complete GUI. The following implementations
are currently available.

- `TerminalGui` - A simple text interface used for demonstration and prototyping.
- `ControlGui` - Used by the impulse test framework to control DSP parameters.

In particular, `TerminalGui` stores a representation of the widgets built by FAUST and allows the value of
a slider to be modified from the terminal while the audio thread continues to execute the DSP.

### Metadata

The `meta` package provides the interface used by the generated code to export metadata associated with the
FAUST program.

### Helpers

The `help` package contains support functions used by the generated code. These utilities simplify the
visitor implementation and keep the produced code more compact and readable.

The package mainly collects mathematical helpers and polymorphic SIMD load and store operations that work
with both pointers and arrays (`vload`, `vstore`).

### Memory

The `mem` package contains utilities for manual buffer allocation and management. This package is mainly
used by the test, benchmark, and inspection architectures.

### Benchmark and Test

The `bench` and `test` packages contain code specific to integration with the benchmark framework and the
backend `impulse-tests`, respectively.

The corresponding top-level architectures remain lightweight: they initialize the DSP, build the required
buffers, and delegate the work to the functions provided by these packages.

## Available architectures

The `.mojo` files located directly in the directory are the templates intended to be passed to FAUST through
the `-a` option.

**portaudio.mojo**

The `portaudio.mojo` architecture integrates the generated DSP with `PortAudio`.

The resulting program:

1. allocates an instance of `mydsp`;
2. initializes the DSP with the sample rate;
3. initializes the `PortAudio` driver;
4. opens and starts the audio stream;
5. keeps the main thread active while `PortAudio` executes the DSP in its callback;
6. stops the driver and frees the instance.

The `PortAudio` driver only supports 32-bit precision, so the architecture checks at compile time that
`DFAUST` corresponds to `f32`.

**portaudio-terminal.mojo**

The `portaudio-terminal.mojo` architecture extends the previous case by adding `TerminalGui`.

After DSP initialization, the interface is built:

```
    var gui = TerminalGui[dfaust]()
    dsp[].build_user_interface(gui)
```

The audio driver is then started normally, while the main thread enters the GUI loop. The user can modify
the parameters exposed by the DSP, and those changes are observed by the subsequent audio computation.

This architecture demonstrates the interaction between the generated DSP, an audio driver, and an
implementation of the FAUST graphical model.

**bench.mojo**

The `bench.mojo` architecture integrates the Mojo code with the benchmark framework.

No real audio driver is used. The architecture directly allocates the input and output buffers, initializes
the DSP, performs a warmup phase, and repeatedly measures `compute`.

The result is converted into a report and can be written in the formats used by the framework, allowing
the Mojo code to be compared with other implementations without introducing the cost or variability of a
real-time audio system.

**inspect.mojo**

The `inspect.mojo` architecture is intended for inspection of low-level code produced by Mojo.

In this case as well, buffers are allocated directly and a DSP instance is initialized, but the kernel is
invoked through a dedicated function:

```
    @no_inline
    @export("inspect_compute")
    def inspect_compute(...)
```

The explicit symbol and disabled inlining make it easier to locate the code corresponding to `compute` and
analyze its assembly or intermediate representations.

The `keep` and `clobber_memory` primitives also prevent the compiler from eliminating the computation
during optimization.

**impulse.mojo**

The `impulse.mojo` architecture integrates the backend with the FAUST impulse test system.

The architecture initializes the DSP and a `ControlGui`, generates the header expected by the framework,
and delegates execution to the utilities contained in `test/impulse`.

The produced samples are printed to standard output. The external framework can then redirect them to `.ir`
files and compare the Mojo backend response with the reference `.ir` implementations.

## Audio execution flow

For a PortAudio application, the complete interaction between components is:

```
    main
    |
    +--> allocate mydsp
    |
    +--> mydsp.init(sample_rate)
    |
    +--> [optional] mydsp.build_user_interface(gui)
    |
    +--> PortAudio.init()
    |
    +--> PortAudio.start(mydsp)
    |        |
    |        +--> read number of DSP inputs/outputs
    |        +--> open stream
    |        +--> register faust_callback
    |
    +--> main thread remains active
    |
    |                  PortAudio thread
    |                       |
    |                       v
    |                faust_callback
    |                       |
    |                       v
    |             mydsp.compute(...)
    |                       |
    |                       v
    |                  audio output
    |
    +--> PortAudio.stop()
    |
    +--> free mydsp
```

The point of contact between components remains `FaustDsp`: the generator produces the class conforming to
the trait, while the architecture decides when and in which context to invoke its operations.

## Compile-time configuration

Several architecture properties are configured at compile time by passing `-D` options to the Mojo
compiler, for example:

```
    mojo build -D DFAUST=DType.float32 -D BUFF_SIZE=128 -D SAMP_RATE=48000 ...
```

The values are then retrieved in the code through functions provided by `std.sys.defines`, such as
`get_defined_dtype` and `get_defined_int`.

The options used by the components include:

- `DFAUST`, which selects the numerical type of the external streams;
- `BUFF_SIZE`, which controls the block size in architectures that expose it;
- `SAMP_RATE`, which selects the sample rate;
- additional options specific to the benchmark and inspection frameworks.

This mechanism allows the architecture to be specialized at compilation time without modifying its source
code.

## Essential workflow

A typical generation combines a FAUST program with an architecture through the `-a` option. For example,
from the repository root:

```
    build/bin/faust \\
    -lang mojo \\
    -a architecture/mojo/portaudio.mojo \\
    path/to/program.dsp \\
    -o path/to/program.mojo
```

The transpiled file can then be compiled by specifying the path to the architecture packages:

```
    mojo build \\
    -I architecture/mojo \\
    path/to/program.mojo \\
    -o path/to/program
```

To use a different architecture, it is sufficient to change the template passed to `-a`:

```
    -a architecture/mojo/portaudio-terminal.mojo
    -a architecture/mojo/bench.mojo
    -a architecture/mojo/inspect.mojo
    -a architecture/mojo/impulse.mojo
```

The separation between generator, common interfaces, and architecture files allows the same Mojo backend
to be used in different execution contexts.
